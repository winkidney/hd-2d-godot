# Ancient 主场景性能分析 · 2026-10-08

当前默认参数在本机具有充足的 60 Hz 计算预算。主要优化机会是 GPU 的不透明物体绘制与景深，以及 CPU 的局部灯阴影处理。角色动画、物理和 HUD 的开销较小。

## 测量对象与条件

- 入口 `scenes/ancient_canal.tscn`，提交 `661452d10bf18a1fc372c8daff7940006c591fa3`。
- 运行时摘要 `1a540a6c3fa4548b7cdbe7636f456ae1384cf0bc58901947c56106cb9cb787c6`，测量前后相同。没有修改场景、运行时脚本、素材或用户设置。
- Ryzen 9 7900X3D、RTX 4070 SUPER、NVIDIA 580.178.04；Godot 4.7.2 官方版 `ed1daf0bf`，Vulkan Forward+。
- 1920×1080，默认 F 跟随镜头，默认黄昏参数，2×MSAA，真实自动行走、碰撞、动画、灯光、水面、六层视差与 HUD。忽略个人保存的参数。
- 后台最小化、无焦点窗口内的独立 SubViewport。时间倍率 1，物理 60 Hz，不使用固定 FPS，采样时没有截图、读回或视频编码。GPU 测量串行进行。
- 原工具分别测量晴昼、黄昏、夜晚，每组预热 5 秒、采样 30 秒。修正条件的对照每组预热 3 秒、采样 10 秒；CPU 计时每组采样 20 秒且完成一圈路线；最终阶段分析采样 8 秒。短对照覆盖同一段路线，不代表所有镜头和位置。
- 42 组测量、7 份报告通过运行条件、绘制计数配对、原始文件校验和及无读回检查，见 [检查汇总](profiling/20261008/metadata/verification-summary.json)。

这些是默认场景的离屏计算与提交测量，未测前台显示呈现、桌面合成、输入延迟、启动加载、VRAM 峰值，也未对任意保存的极端参数做验收。不能把计算预算直接换算为玩家实际看到的 FPS。

## 先校正现有基准

发现现有 `tools/ancient_canal/benchmark.gd` 的两项偏差。

1. 最小化窗口触发 Godot 的后台休眠。即使 `Engine.max_fps=0`、`OS.low_processor_usage_mode=false`，窗口不可绘制时仍会使用 `low_processor_usage_mode_sleep_usec`。原工具三个时段的墙钟 P95 为 7.554/7.349/7.371 ms，这些值包含休眠，不能归因于场景计算。[本版本 OS 源码](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/core/os/os.cpp#L671)和[主循环调用](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/main/main.cpp#L4795)说明了该行为。
2. 新建 SubViewport 默认不启用 MSAA，没有自动继承主窗口的 2×MSAA。实际读取到主窗口枚举值 1、原始 SubViewport 枚举值 0，见 `confirm/performance-report.json`。

本次在独立生成的测试副本里将后台休眠设为 0，并显式设置 2×MSAA。历史工具和历史证据保留。以下主要结论采用修正后的测量。

黄昏基准 GPU 均值 **2.023 ms**、P95 **2.364 ms**；CPU 视口渲染均值 **0.553 ms**、P95 **0.697 ms**；绘制回调间隔 P95 **2.549 ms**。独立复测 GPU 均值 2.022 ms，CPU 均值 0.557 ms。

CPU 视口计时不含脚本和物理；帧设置额外约 0.01 ms。CPU 与 GPU 可以重叠执行，不能简单相加。计时器可能对应较早的提交，`frame_post_draw` 不是 GPU 完成栅栏。依据见 [RenderingServer 计时说明](https://docs.godotengine.org/en/stable/classes/class_renderingserver.html#class-renderingserver-method-viewport-get-measured-render-time-cpu)。

## GPU 与渲染线程热点

下表来自独立开启 `--gpu-profile` 的阶段采样，352 个去重的 RenderingDevice 帧。阶段分析会增加计时标记和输出开销，不能与未开启 profiling 的整帧计时机械相加。

| 阶段 | GPU 均值 ms | CPU 提交/处理均值 ms |
|---|---:|---:|
| 不透明物体绘制 | 0.547 | 0.047 |
| 景深 | 0.490 | 0.003 |
| 深度预处理 | 0.183 | 0.053 |
| 局部灯阴影绘制 | 0.183 | 0.196 |
| 主光阴影绘制 | 0.090 | 0.064 |
| 屏幕空间反射 | 0.149 | 0.017 |
| 泛光 | 0.099 | 0.003 |
| 环境遮蔽 | 0.082 | 0.011 |
| HUD/画布 | 0.023 | 0.012 |

不透明物体与景深占主要 GPU 时间。局部阴影除表中的约 0.196 ms 提交外，还需要六面的裁剪与查询，合计约 0.157 ms CPU。连同主光阴影提交约 0.064 ms，阴影相关处理是 CPU 渲染中的主要部分。

原始 GPU 时间戳采用本版本 Vulkan 后端实际返回的纳秒，CPU 时间戳为微秒。新采样将大整数 GPU 时间戳保存为字符串，避免丢失精度。初期文件的 `gpu_us` 字段名有误，其值实际为纳秒；汇总按纳秒计算，并与引擎输出交叉核对。单位依据见[对应 Vulkan 实现](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/drivers/vulkan/rendering_device_driver_vulkan.cpp#L6107)。明细见 [阶段汇总](profiling/20261008/metadata/gpu-stage-summary-corrected.json)。

## CPU 脚本热点

计时器只加在 build 目录里的当前脚本副本，正式脚本保持原样。以下是每次调用的耗时，包含计时器的少量开销。父函数包含子函数，表中各行不能相加。

| 函数 | 均值 ms/次 | P95 ms/次 | 调用次数/20秒 |
|---|---:|---:|---:|
| 场景每帧更新，含子调用 | 0.0693 | 0.0820 | 8309 |
| 相机与视差更新，含子调用 | 0.0501 | 0.0600 | 8309 |
| 六层视差更新 | 0.0335 | 0.0410 | 8309 |
| 镜头跟随 | 0.0077 | 0.0090 | 8309 |
| 角色物理更新，含动画 | 0.0452 | 0.0880 | 1200 |
| 动画更新，含帧绑定 | 0.0130 | 0.0210 | 1200 |
| 颜色/法线/蒙版绑定 | 0.0051 | 0.0080 | 1200 |
| 云层移动 | 0.0045 | 0.0050 | 8309 |

场景 `_process` 约 0.069 ms；角色每次物理更新约 0.045 ms、每秒 60 次。脚本中六层视差最值得简化，但它的绝对成本仍远小于 GPU 和阴影处理。

仅在测试副本中让自然视差跳过不必要的逐帧投影及 transform 写入，`parallax.update` 从 0.0335 降至 0.0010 ms，场景 `_process` 从 0.0694 降至 0.0373 ms。完整渲染耗时没有可靠改善，不能宣称这能提高约一倍 FPS，也没有证据证明它能解决阴影重绘。艺术视差模式、模式切换、状态恢复和诊断数据仍需保持原契约。

`actor.gd` 在每次 60 Hz 物理更新中绑定三张图集和帧区域，即使帧索引没变；本次约 0.0051 ms/次。可缓存最后绑定的方向、帧号和材质状态，但优先级低。

## 逐项关闭对照

以下采用修正后的同条件黄昏测试。收益按 GPU 或 CPU **渲染均值**分别计算。负数表示略慢；小于几个百分点的结果容易受频率、路线取样和系统调度影响。关闭或隐藏测试是成本估计，不是最终画面方案；各项收益不能相加。

| 测试 | GPU ms | GPU 降低 | CPU 渲染 ms | CPU 降低 |
|---|---:|---:|---:|---:|
| 默认 | 2.023 | 0.0% | 0.553 | 0.0% |
| 关闭景深 | 1.504 | 25.6% | 0.543 | 1.9% |
| 关闭局部灯阴影 | 1.796 | 11.2% | 0.246 | 55.5% |
| 关闭全部阴影 | 1.601 | 20.9% | 0.173 | 68.7% |
| 关闭主光阴影 | 1.843 | 8.9% | 0.472 | 14.7% |
| 关闭两盏大灯阴影 | 1.944 | 3.9% | 0.464 | 16.2% |
| 关闭 SSR | 1.841 | 9.0% | 0.530 | 4.1% |
| 关闭泛光 | 1.870 | 7.5% | 0.553 | 0.1% |
| 关闭 SSAO | 1.947 | 3.8% | 0.545 | 1.5% |
| 隐藏近镇 | 1.880 | 7.1% | 0.511 | 7.7% |
| 隐藏远镇 | 1.996 | 1.4% | 0.541 | 2.1% |
| 关闭法线开关 | 2.011 | 0.6% | 0.570 | -3.0% |
| 关闭 2×MSAA | 1.850 | 8.6% | 0.554 | -0.2% |
| 3D 渲染比例 75% | 1.435 | 29.1% | 0.545 | 1.5% |
| 关闭 SSAO/SSR/景深/泛光 | 0.952 | 52.9% | 0.499 | 9.7% |
| 自然视差跳过逐帧更新 | 2.031 | -0.4% | 0.554 | -0.1% |

独立复测再次确认：关闭景深约节省 25% GPU；关闭局部灯阴影约节省 56% CPU 渲染和 11% GPU。

另外实测 **景深中档降到低档**，保持景深开启、模糊量与焦点保护不变，GPU 总均值从 2.022 降到 **1.720 ms**，节省 **14.9%**。这是当前最容易试用的质量折中，需对照近景/远景散景颗粒和人物边缘。Godot 的中档/低档枚举及质量含义见 [DOF 文档](https://docs.godotengine.org/en/stable/classes/class_renderingserver.html#enum-renderingserver-dofblurquality)。

关闭“法线开关”没有可靠收益；这个测试对建筑材质只设置 normal_scale=0，并不移除所有 normal-map 采样。它支持先保留角色的逐帧法线演示，不支持“所有法线计算完全免费”的结论。

## 场景复杂度

- 315 个 MeshInstance3D、315 个 surface、约 **444,171 个源三角形**、75 份不同网格资源、315 份不同材质实例。Sprite3D 不计入这个网格清单；帧中的 primitives 也会受裁剪和 mesh LOD 影响。
- 代表帧约 298～300 次可见绘制调用、约 800～900 次阴影绘制调用；局部灯共 10 盏启用投影。立方阴影裁剪涉及每灯六面，主方向光为四级分割。调用数不等于独立模型数或唯一三角形数。
- 一棵柳树 **19,784 面**，一座民居 **8,516 面**，酒肆 **12,112 面**。
- 近镇 16 座房屋、7 棵柳树，远镇 8 座房屋，合计源面数 **342,872**，约占网格总量 **77.2%**。删除整个近镇仅带来约 7% 的 GPU 改善，说明不能把面数占比当作同等耗时占比；减少这些面数仍有利于较弱硬件和影子通道。
- `world.prepare_model()` 每个 surface 都 duplicate 材质，导致重复模型也拥有独立材质。材质实例独立不等于贴图像素被复制 315 次。

几何清单见 [模型统计](profiling/20261008/metadata/model-inventory.json)。

## 优化顺序与验收条件

| 优先级 | 建议 | 本次证据与验收重点 |
|---|---|---|
| 1 | 提供景深低档质量选项，保持当前景深开关、焦点保护和模糊量 | 已测 GPU 总耗时约降低 15%；用 F/W 镜头及近/远景对照散景、角色轮廓。默认是否采用等待画面比较。 |
| 2 | 按距离和画面贡献筛选局部投影灯，优先保留酒肆/布摊两盏大灯；装饰灯继续照明，可去掉实时阴影或采用较简单投影 | 关闭全部局部阴影是约 56% CPU、11% GPU 的上限；只关闭两盏大灯节省约 16% CPU，收益并不能覆盖全部局部灯成本。保留冷暖法线受光、桥栏/建筑遮挡关系和近灯阴影。 |
| 2 | 试验主光阴影两级分割、较短投影距离以及近镇远处模型的阴影距离淡出 | 当前主光投影距离 70m、四级分割；关闭主光约节省 15% CPU、9% GPU。具体改成两级或缩距尚未实测，必须覆盖沿岸、桥面、边界及 F/W 镜头，检查阴影跳变。 |
| 3 | 柳树与远景房屋做 LOD/HLOD，远镇可用简化网格或经复核的 impostor | 先试柳树约 2k～4k、远镇房屋约 0.5k～1.5k 面，这是制作目标而非已验证最佳值。保留柳条轮廓、屋顶层次、六层视差位置和原始可重建资产。 |
| 3 | 缓存共享材质；相同子网格按街区使用 MultiMesh | 减少独立状态和绘制提交。共享材质本身不保证减少 draw calls；MultiMesh 必须按空间分块，因为单组实例不能逐个视锥裁剪。所有全局法线调节仍要同步。 |
| 4 | 自然视差只在镜头/模式/参数改变时刷新必要数据；动画绑定按方向/帧/材质变化更新；HUD 文本按值变化写入 | 逻辑更新绝对值很小，视差试验节省约 0.032 ms/次且没改善总 GPU 时间；保持模式恢复、相机居中、108 帧颜色/法线/蒙版和输入契约。 |
| 5 | SSR、SSAO、泛光和 3D 渲染比例做性能档位 | SSR 约 9%、SSAO 约 4%、泛光约 8% GPU；75% 3D 比例约 29%，但也降低 Sprite3D 的实际采样分辨率。对像素角色清晰度影响较大，不作为首选默认。 |

[Godot HLOD 文档](https://docs.godotengine.org/en/stable/tutorials/3d/visibility_ranges.html)支持按距离换网格、精灵及材质；[MultiMesh 文档](https://docs.godotengine.org/en/stable/tutorials/performance/using_multimesh.html)说明了整组裁剪边界。上述未实现方案的收益要在修改后独立复测，不能采用关闭整组效果的结果代替。

每一步使用同一运行时摘要、同一段实际路线及相同分辨率，单项实施后测量均值/P95和绘制计数，再单独做实际 GPU 画面对照。生产优化影响运行时后须按项目规则执行 `make test` 与对应 Ancient 回归。本次没有改生产逻辑，验证范围是 profiler 实际运行与原始证据完整性。

## 证据与复现

完整原始数据已持久归档到 [profiling/20261008](profiling/20261008/README.md)。逐帧 JSON 使用 gzip 无损压缩，原始报告与采样记录保持原样；原始 build 路径由归档清单映射，不需要本机缓存目录。归档包括 42 组采样、7 份报告、当次生成脚本、基准源码和校验记录。

[summary.json](profiling/20261008/summary.json)保存整帧均值与分位数、GPU 阶段、CPU 函数、全部对照和复测结果。共享法线开关的 0.6% 差异保留“并非独立角色法线测试”的边界。

在项目根运行 `python3 tools/ancient_canal/verify_profile_archive.py`，无需 Godot 或 GPU，即可验证归档的字节摘要和原始关联，重算并核对 summary。归档不包含日志、着色器缓存、管线缓存及个人用户目录。

使用当前安装的 Godot，在项目根目录运行下列命令。输出目录必须是新的 build 子目录，避免覆盖历史证据。

```sh
python3 tools/ancient_canal/profile.py --output build/ancient-canal/profile-new --cases baseline,dof_low,no_dof,no_local_shadows --seconds 10 --warmup 3
python3 tools/ancient_canal/profile.py --output build/ancient-canal/profile-cpu-new --cases baseline,static_natural --seconds 20 --warmup 3 --instrument-cpu
python3 tools/ancient_canal/profile.py --output build/ancient-canal/profile-stages-new --cases baseline --seconds 8 --warmup 3 --gpu-profile
```

复现工具是 `tools/ancient_canal/profile.py`。它根据当前 benchmark 和脚本生成 build 内的独立探针，对插入点做精确检查，保留源摘要及生成副本；不安装依赖、不运行服务器、不加载日常用户设置。运行结束自动退出所创建的 Godot 进程。
